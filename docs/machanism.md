# KDAA AFE 동작 원리

이 문서는 프로그램이 **무엇을 입력받아, 어떤 계산을 거쳐, 무엇을 내보내는지**를 설명합니다.
요구사항 자체는 [`spec.md`](../spec.md)가 기준이고, 여기서는 그 요구사항이 코드에서 어떻게 구현되는지 다룹니다.

---

## 1. 한 줄 요약

> 키보드를 칠 때 나는 **소리 한 번(키 입력 1회)** 을 스펙트로그램 이미지 한 장으로 바꾸고,
> CNN이 그 이미지를 보고 **"어떤 키였을 확률"** 을 38개 후보에 대해 계산한다.
> 그중 확률이 높은 **상위 N개(기본 5개)** 를 LM 서버에 넘긴다.

이 프로그램(AFE, Acoustic Front-End)은 **글자를 확정하지 않습니다.** "ㄱ일 확률 72%, ㄷ일 확률 16%…" 처럼
*불확실성을 그대로 남겨서* 넘기고, 음절 조합·오타 교정·문맥 판단은 뒤에 있는 LM 서버가 맡습니다.

```
녹음기(48kHz) ─► [Mel 컴포넌트] ─► [AFE: CNN] ─► [LM 서버]
                  키 입력 감지          38개 심볼        자모 → 음절 → 문장
                  100ms 자르기          top-N 확률        (사전, 언어모델)
                  log-mel 변환
```

AFE의 범위는 가운데 상자 하나뿐입니다. 오디오를 직접 만지지 않으며(Mel 컴포넌트 담당),
음절도 만들지 않습니다(LM 서버 담당, 설계 결정 D6).

---

## 2. 왜 소리로 키를 알아낼 수 있나

키보드는 키마다 **누르는 위치·스위치 구조·판의 진동 전달 경로**가 조금씩 달라서,
키를 칠 때 나는 소리의 주파수 성분이 키마다 미묘하게 다릅니다. 사람 귀에는 거의 같아 보이는 소리여도
스펙트로그램으로 보면 **어느 주파수 대역에 에너지가 언제 몰리는지**가 달라집니다.
CNN은 이 "무늬"를 이미지처럼 학습합니다.

한계도 분명합니다. 키 사이 차이가 작아서 **확실히 하나로 못 정하는 경우가 흔합니다.**
이것이 top-1이 아니라 **top-N 확률 분포**를 출력하는 이유입니다(§5).

---

## 3. 입력: 키 입력 1회 = log-mel 이미지 1장

AFE는 Mel 컴포넌트가 만든 텐서를 **그대로** 받습니다. (`src/melio.py`)

| 항목 | 값 |
|---|---|
| 샘플레이트 | 48 kHz, mono |
| 창 길이 / 이동 | 8 ms(384샘플) / 2 ms(96샘플) |
| 멜 밴드 | 64개, 200 Hz ~ 20 kHz |
| 구간 길이 | 100 ms (키 입력 시점 −5 ms ~ +95 ms, 누름+뗌 포함) |
| 시간 프레임 | 48개 고정 |
| 값 | `log(mel + 1e-6)` 후 **클립별 z-score**(평균 0, 표준편차 1) |
| 최종 모양 | `float32`, `(1, 64, 48)` = (채널, 주파수, 시간) |

- **log**: 소리 크기는 로그 스케일로 보는 것이 사람 귀·모델 모두에 잘 맞습니다.
- **클립별 z-score**: 키를 세게 치든 약하게 치든, 마이크에서 멀든 가깝든 **전체 크기 차이를 지우고 "모양"만** 남깁니다.
- **48프레임 고정**: CNN이 고정 크기 입력을 받기 때문입니다. (길면 가운데를 자르고, 짧으면 가장자리를 채움 — Mel 쪽 책임)

### 3.1 입력 검증 — "조용히 틀리지 않기"

학습할 때와 배포할 때 log-mel 만드는 방식이 조금만 달라도 모델은 **에러 없이 엉뚱한 답**을 냅니다(도메인 시프트).
그래서 AFE는 입력이 약속과 다르면 **바로 예외를 던집니다.**

- `check_logmel()`: 모양이 `(64,48)` 또는 `(1,64,48)`인지, 실수형인지, NaN/Inf가 없는지 확인 (AC-8)
- `MelSession.check()`: 버전·샘플레이트·`n_mels`·`frames`, 그리고 **`param_hash`** 가 학습 때와 같은지 확인.
  `param_hash`는 "추출 파라미터 전체를 해시한 지문"이라 파라미터가 하나라도 바뀌면 달라집니다(NFR-2)
- `idx`가 0부터 빈틈없이 이어지는지, `onset_s`가 시간순인지도 확인

## 4. 분류 모델: SmallCNN

`(B, 1, 64, 48)` 이미지 → `(B, 38)` 점수(logit). 구조는 `src/model.py`의 `SmallCNN`입니다.

```
입력 (1, 64, 48)
 └ [Conv3×3 → BatchNorm → ReLU → MaxPool2]  채널 16 → (16, 32, 24)
 └ [Conv3×3 → BatchNorm → ReLU → MaxPool2]  채널 32 → (32, 16, 12)
 └ [Conv3×3 → BatchNorm → ReLU → MaxPool2]  채널 64 → (64,  8,  6)
 └ [Conv3×3 → BatchNorm → ReLU → MaxPool2]  채널 96 → (96,  4,  3)
 └ Flatten (1152) → Dropout(0.2) → Linear → 38개 점수
```

- **Conv**: 작은 필터로 "특정 주파수 대역의 특정 시간대 에너지 패턴"을 찾습니다. 층이 깊어질수록 더 큰 무늬를 봅니다.
- **MaxPool**: 해상도를 절반으로 줄여 계산량을 줄이고 미세한 위치 흔들림에 둔감하게 만듭니다.
- **Flatten 후 Linear** (평균 풀링 대신): 키 소리는 *어느 주파수에서 언제* 나는지가 중요하므로 위치 정보를 버리지 않습니다.
- **일부러 단순하게**: ESP32-S3에 올릴 때 int8 변환이 잘 되는 연산(Conv/BN/ReLU/MaxPool/FC)만 썼습니다.

구조에서 손으로 계산한 규모 (실행해서 잰 값이 아님):
파라미터 약 12.3만 개 → int8이면 약 120 KB(예산 ≈1 MB 이내), 곱셈-덧셈 약 1,000만 회.
`coatnetlite`(합성곱+어텐션)는 오프라인 비교용이며 배포 대상이 아닙니다.

### 4.1 38개 클래스 — 특수 키도 그냥 클래스

출력 38개 = 한글 기본 자모 33개 + 특수 토큰 5개(`<sp>` 스페이스, `<bs>` 백스페이스, `<shift>`, `<caps>`, `<other>`).
Space·Backspace도 **별도 처리 없이 같은 분류기의 클래스 하나**입니다(D3). 특수 키를 잘 구분하는지는 실제 데이터로
확인해야 하며, 그 기준이 keytype 정확도 ≥ 95%(AC-4)입니다. "Shift+ㄱ = ㄲ" 같은 해석은 LM 서버 몫입니다.

## 5. 출력: 점수 → 확률 → top-N (`src/infer.py`)

모델이 내는 38개 점수(logit)를 다음 순서로 가공합니다.

**① softmax(온도 T 적용)** — 점수를 합이 1인 확률로 바꿉니다.

```
p_i = exp(z_i / T) / Σ_j exp(z_j / T)
```

T=1이면 보통 softmax. T>1이면 분포가 평평해지고(덜 확신), T<1이면 뾰족해집니다.

**② 상위 N개 선택** — 확률 내림차순으로 N개(기본 5). 확률이 같으면 번호가 작은 클래스를 먼저 둡니다.
그래서 **같은 입력이면 항상 같은 출력**이 나옵니다(AC-7).

**③ 재정규화** — 뽑힌 N개의 확률을 합이 1이 되도록 다시 나눕니다(AC-9).

```
예) 전체 분포에서 ㄱ 0.60, ㄷ 0.13, ㅋ 0.10, (나머지 상위 2개 합 0.07) → 합 0.90
    → 각각 0.90으로 나눠 ㄱ 0.667, ㄷ 0.144, ㅋ 0.111, ... (합 1.0)
```

**④ keytype 도출** — 1등 심볼로 `normal | space | backspace | shift | caps | other` 를 정합니다.

이렇게 만든 `kdaa.afe.v1` JSON이 LM 서버로 갑니다.

```json
{ "idx": 3, "onset_s": 1.402, "keytype": "normal",
  "alts": [ {"jamo":"ㄱ","p":0.72}, {"jamo":"ㄷ","p":0.16}, {"jamo":"ㅋ","p":0.12} ] }
```

### 5.1 왜 top-1이 아니라 top-N인가

키 소리로는 ㄱ/ㅋ/ㄷ처럼 비슷한 키를 자주 헷갈립니다. 1등만 넘기면 틀린 순간 LM이 복구할 방법이 없지만,
정답이 상위 5개 안에만 있으면 LM이 **단어 사전·문맥으로 골라낼 수 있습니다.**
그래서 평가에서 **top-N coverage**(정답이 상위 N개 안에 든 비율)가 "LM이 복구 가능한 상한선"으로 가장 중요한 지표입니다(FR-7).

### 5.2 온도 보정 (Calibration, `src/calibrate.py`)

신경망은 실제 정확도보다 **과하게 확신**하는 경향이 있습니다(예: 70%만 맞히는데 확률은 99%로 출력).
LM이 확률 크기를 믿고 계산에 쓴다면 이건 문제입니다. 해결은 검증 데이터에서 **온도 T 하나**를 찾는 것입니다.

- 검증 데이터의 NLL(정답 확률의 로그 손실)을 최소화하는 T를 황금분할 탐색으로 찾습니다
  (NLL이 β=1/T에 대해 볼록이라 안정적으로 수렴).
- 품질은 **ECE**로 봅니다: 확신도 구간별로 "말한 확률"과 "실제 정답률"의 차이를 가중 평균한 값. 목표 ≤ 0.05(AC-5).
- 순위는 안 바뀌고 확률 크기만 바뀝니다. 결과는 `calibration.json`에 저장되고, 추론 시 자동으로 적용되며
  출력의 `meta.calibrated`가 `true`가 됩니다.

## 6. 학습 (`src/dataset.py`, `src/train.py`)

**데이터**: 키 입력마다 (log-mel 이미지, 정답 심볼) 한 쌍. 정답은 키로거(실제로 누른 키 기록)에서 옵니다.
공격 시에는 키로거가 없고, **학습할 때만** 정답 라벨로 씁니다.

**분할이 중요합니다.** 무작위로 섞어 나누면 같은 녹음 세션의 인접 샘플이 학습·테스트 양쪽에 들어가서
정확도가 **부풀려집니다**(마이크 위치·소음 같은 세션 특성을 외워버림). 그래서:

- `session` 분할(기본): 한 세션은 통째로 train/val/test 중 한 곳에만 들어갑니다(FR-6).
- `participant` 분할: 처음 보는 사람에게도 통하는지(일반화)를 봅니다.
- 분할 결과는 `split.json`에 저장해서, 평가·보정·내보내기가 **같은 분할**을 씁니다. 시드도 고정(NFR-4).

**학습 루프**: 교차 엔트로피 손실 + AdamW + 코사인 학습률 감소. 에폭마다 검증 정확도를 재고
**가장 좋은 에폭의 가중치**를 `best.pt`로 저장합니다. 특수 키가 적을 때를 위한 클래스 가중치 옵션도 있습니다.

## 7. 평가 (`src/evaluate.py`)

| 지표 | 의미 |
|---|---|
| top-1 / top-5 | 1등 / 상위 5개 안에 정답이 있는 비율 |
| top-N coverage | LM이 복구할 수 있는 상한선 (목표: near 조건에서 top-5 ≥ 95%) |
| 시나리오별 정확도 | near / far / noise 각각. far·noise는 떨어져도 되고 따로 보고 |
| keytype 정확도 | 스페이스·백스페이스 등을 맞혔는지 (목표 ≥ 95%) |
| 혼동 행렬 | 어떤 키끼리 헷갈리는지 (ㄱ↔ㅋ 등) |
| ECE | 확률이 얼마나 정직한지 (보정을 쓸 때) |

결과는 `metrics.json`과 **흑백 그림**(혼동 행렬, 시나리오별 막대, 신뢰도 곡선, 학습 곡선)으로 저장됩니다.
`acceptance` 항목이 AC-3/4/5를 통과/실패/측정불가(null)로 판정해 줍니다.

## 8. ESP32-S3로 내보내기 (`src/export_esp32.py`)

마이크로컨트롤러에는 GPU도, 넉넉한 메모리도 없습니다(SRAM ≈512 KB). 그래서 두 단계로 변환합니다.

```
PyTorch(float32) ─► ONNX ─► TFLite int8 (TensorFlow Lite Micro에서 실행)
```

**int8 양자화**는 32비트 실수 가중치·활성값을 8비트 정수로 줄이는 것입니다(크기 ≈1/4, 정수 연산이라 빠름).
실수 `x`와 정수 `q`는 두 숫자 `scale`, `zero_point`로 대응됩니다.

```
q = round(x / scale) + zero_point      (−128 ~ 127로 자름)
x ≈ (q − zero_point) × scale
```

- **PTQ(학습 후 양자화)**: 학습이 끝난 모델에 대표 샘플(기본 300개)을 흘려보내 값의 범위를 재고 `scale`을 정합니다.
- **입력 양자화 값을 Mel 쪽에 넘겨야 합니다.** 기기에서는 Mel 출력이 int8로 바뀐 뒤 CNN에 들어가므로,
  `deployment.json`에 입력의 `(scale, zero_point)`를 기록해 Mel 컴포넌트와 공유합니다.
- 양자화는 정확도를 조금 깎습니다. int8 모델의 top-1이 float 모델보다 **2%p 이하** 하락이어야 통과입니다(AC-6).
  확률값이 흐트러질 수 있어 내보낸 뒤 다시 검증합니다.

## 9. 스트리밍 (`AFEStream`)

배치 모드는 세션 전체를 받아 한 번에 처리하고, 스트리밍 모드는 **키 입력이 올 때마다 토큰 하나씩** 즉시 내보냅니다.
각 키 입력은 서로 독립적으로 계산되므로 결과는 배치와 같습니다(부동소수점 반올림 수준의 ~1e-6 차이 제외).
`idx` 누락, 시간 역전, 잘못된 모양이 들어오면 예외를 던지고 그 입력은 기록되지 않습니다.
호스트에서 잰 지연 시간은 참고용이며, 실제 30 ms 예산은 기기에서 재야 합니다.

## 11. 알아둘 점

- 이 코드의 정확도·지연 시간·int8 손실은 **아직 실제 데이터와 기기에서 측정되지 않았습니다.**
  개발 환경(Codespace)에서는 모델 학습·내보내기를 실행하지 않았고, 후처리·검증·보정·평가 로직만 테스트했습니다.
- 스펙이 정하지 않은 부분(`param_hash` 정의, 클립 파일 이름 규칙 등)은 `README.md`의 "Decisions where the spec is silent"에 정리되어 있습니다.
